# 快照容量与函数尺寸

本文说明索引快照的容量准入预算，以及 REQUEST 函数按处理器需求选择尺寸的依据，供架构师和维护者使用。它支撑[项目总览](overview.md)中可靠检索的目标，不能代替目标环境的容量验收。读完后，你可以理解两种尺寸如何得出、哪些输入已测，以及如何复核或回滚默认值。

服务对快照读写共同采用
`64 × JSON 字节数 + 8 × 向量文件字节数 <= 256 MiB`。
这是依据目标目录和本地峰值校准的容量准入策略，不是进程 RSS 的数学上界。
以下为本地合成容量实验的历史摘要；原始进程记录不随公开样例发布。

## 测量条件与结果

夹具将仓库完整的 500 个工具放在单个 Gateway，包含真实 BM25、归一化向量、
父索引和安全目录。每工具 3 条已批准例句形成 2000 行 1024 维向量，
编码大小为 9,451,128 B、加权大小为 139.34 MiB；6 条例句形成 3500 行
1024 维向量，编码大小为 16,021,863 B、加权大小为 212.27 MiB。
加权大小不是快照文件大小，也不能与 RSS 直接相加。

以下峰值来自本地 macOS 进程，不是 Lambda 实测值。前三项各运行 3 个新进程，
最后一项运行 1 个新进程，均使用完整的 6 条例句场景和原样 256 MiB 准入常量；
测量前后源码摘要一致，10 个进程均退出 0。

| 实际路径 | 最高本地 RSS（MiB） | 对比函数配置（MiB） | 算术余量（MiB） |
|---|---:|---:|---:|
| 完整快照加载 | 185.375 | Search 2048 | 1862.625 |
| 旧新两份完整增强索引共存并交换 | 197.3125 | Search 2048 | 1850.6875 |
| 增强生成、原索引复核、序列化及上传回读 | 417.171875 | Enhancer 1024 | 606.828125 |
| 六词典常驻、SDK 导入后完整增强发布 | 731.09375 | 最小索引函数 1024 | 292.90625 |

增强流程实际执行序列化、1006 次磁盘 PUT 和 2019 次 GET（含完整性回读），
没有用保存请求历史的内存假服务放大驻留。它产生 3,584,000 个 Python 浮点数及
列表，按实际对象大小估算为 111.62 MiB；输入 matrix、初载向量及增强向量各为
13.67 MiB，另包含原索引重载。两份完整增强索引共存时向量合计 28,672,000 B；
交换后的测量探针不继续持有旧对象。

压力项显式保留 6 个不同配置的真实分词器，缓存上限仍为 4。SDK 仅做真实导入，
当前 RSS 从 40.05 增至 58.09 MiB，六词典就绪后为 487.09 MiB；
没有创建真实 AWS/HTTP 客户端或构造真实异常请求链。前三项没有预先导入 SDK，
因此压力项单独列出。

## 256 MiB 的推导与限制

原 128 MiB 预算会拒绝上述 139.34 MiB 和 212.27 MiB 的正常目标目录。
当前预算取最小索引函数配置 1024 MiB 的四分之一，即 256 MiB，读写保持一致；
Search 配置为 2048 MiB，Indexer 和 Enhancer 均为 1024 MiB。
最重本地压力峰值为 731.09375 MiB，距 1024 MiB 尚有 **292.90625 MiB**，
达到至少 256 MiB 本地安全余量的校准目标。

经验分解是约 487 MiB 压力基线和约 244 MiB 增量，可落在
512 MiB 固定开销、256 MiB 恢复工作量、256 MiB 余量的配置划分内。
这不构成所有输入的证明。双区域合成测试约束共同预算不超过
Search、Indexer、Enhancer 最小配置的四分之一；3/6 条例句的容量回归覆盖目标读写。

目标 Lambda 的实际 RSS、网络缓冲、冷启动及线上 SLO 仍需部署测量。
自定义超长词典、超大模型输出和任意合法输入的最坏峰值未获保证。
三个下载线程的 256 KiB 分块只约束应用下载块，不能代表 SDK、词典、
旧新索引或增强生成的总内存。原始输出继续保存在仓库外，不作为产品文件提交。

## REQUEST 默认尺寸与回滚

REQUEST 的 **1769 MB 是正式默认值**，定义在[函数尺寸表](../infra/functions.py)，
会用于两个区域和所有部署阶段。它不是临时实验开关；当前部署配置没有内存覆盖字段。
Search 保持 2048 MB，Indexer 和 Enhancer 保持 1024 MB。REQUEST 不加载快照，
因此不参与上面的快照恢复预算推导。

vCPU 是平台分配给函数的处理器计算份额。Lambda 根据内存配置分配计算能力，
1769 MB 对应约 1 个完整 vCPU；依据是[官方内存配置说明](https://docs.amazonaws.cn/en_us/lambda/latest/dg/configuration-memory.html)，
核对日期为 2026-10-13。提高 REQUEST 内存的目的是缩短首次服务对象创建时间，
不是容纳更大的目录。

首次初始化（`handler.factory`）发生在执行环境第一次处理请求时，应用会创建服务对象、
读取配置并准备客户端。平台初始化（`Init Duration`）发生在请求处理函数开始执行前，
包括运行时准备、代码加载和模块级初始化。二者分别计时；以下对照只证明前者明显缩短。

提高内存同时增加每单位执行时间的计费用量，需测量同负载下的初始化、冷/热时延和 GB-s。当前默认值不是费用最优承诺。未新增 REQUEST Duration 告警。

若后续决定回退到 256 MB，按以下步骤形成经审核的变更：

1. 将[函数尺寸表](../infra/functions.py)中 REQUEST 的内存改回 256，
   同步修改[双区域内存断言](../tests/infra/test_components.py)；不改变三个索引函数或快照预算。
2. 按 [README 构建及验证](../README.md#构建及验证)运行测试与两区离线 synth，
   重新计算 REQUEST 时延、并发需求和费用假设，并准备变更集。
3. 按[部署顺序](deploy.md#获授权后的部署顺序)审核内存、超时、并发、新旧发布版本、
   alias 和配置摘要，批准后再部署。部署后回读实际内存与版本，并重新验证冷、热请求。

临时切回旧 alias 不能恢复 IaC 默认值，下次部署仍可能变回 1769 MB。
执行回滚或部署前，应按上述步骤审核候选并核对实际配置。
